## 1. 现状与动机

### 1.1 装备页目前是占位符

`src/game.js` 的 `gear` 分支只渲染一行死数据：

```
🗡️ 武器
   未装备 · 开发中                        [空]
装备系统将在下个版本加入
```

也就是说 **UI 已经向玩家承诺了这个功能**。所以这次决策实质只有三种：

- **做** —— 兑现承诺
- **不做并删掉该页** —— 撤回承诺
- **不做并保留占位** —— 继续拖着（最差的选项，玩家点了会失望）

### 1.2 现在玩家几乎没有决策空间

游戏当前的全部操作只有「买 5 个技能」：

| 可做的事 | 频率 | 决策含量 |
| --- | --- | --- |
| 买技能（攻击/生命/攻速/暴击/回复） | 金币够就点 | 低——谁便宜买谁 |
| 看自动战斗 | 全程 | 零 |

放置游戏靠「离线积累 + 回来做一次有意义的选择」驱动留存。
**现在只有积累，没有选择。** 这是装备系统真正的价值，而不是「加点数值」。

### 1.3 但设计约束很强

| 约束 | 含义 |
| --- | --- |
| 「全程无需操作」 | 装备**不能**要求战斗中手动操作 |
| 单文件零依赖 | 不能引入 UI 框架，必须手写 DOM |
| 右栏仅 340px | 背包不能做成大格子 |
| 存档 ≤64KB、原子写 | 物品必须紧凑编码 |
| 已有 v1 存档 | 必须走 `migrate()` 升级，不能让老玩家清零 |

## 2. 核心设计（推荐方案）

### 2.1 一句话

> **4 个槽位、5 档品质、5 种词条、自动装备为主、手动微调为辅。**

### 2.2 槽位

| 槽位 | 图标 | 主属性 | 对应现有属性 |
| --- | --- | --- | --- |
| 武器 | 🗡️ | 攻击 | `atk` |
| 护甲 | 🛡️ | 生命 | `maxHp` |
| 饰品 | 💍 | 暴击 | `crit` |
| 符文 | 🔮 | 攻速 / 回复 | `speed` / `regen` |

**不新增任何战斗机制**——词条只作用于已有的 5 个属性。
这是本方案最重要的取舍：装备系统的复杂度全部落在「物品与背包」，战斗逻辑一行不动。

### 2.3 品质与词条数

| 品质 | 颜色 | 词条数 | 掉落权重 |
| --- | --- | --- | --- |
| 普通 | 灰 `#8a90b0` | 1 | 60 |
| 精良 | 绿 `#4ade80` | 2 | 26 |
| 稀有 | 蓝 `#4d9eff` | 3 | 10 |
| 史诗 | 紫 `#a878e8` | 4 | 3.4 |
| 传说 | 金 `#ffcc4d` | 5 | 0.6 |

### 2.4 词条池（只映射已有属性）

| 词条 | 说明 | 单条数值（按物品等级 `ilvl`） |
| --- | --- | --- |
| 锋利 | 攻击力 +X | `round(1 + ilvl * 0.5)` |
| 坚固 | 最大生命 +X | `round(8 + ilvl * 3)` |
| 疾风 | 攻速 +X% | `2 + ilvl * 0.35`（上限 25%） |
| 锐利 | 暴击率 +X% | `1 + ilvl * 0.25`（上限 12%） |
| 再生 | 每秒回复 +X | `0.2 + ilvl * 0.08` |

品质决定词条**条数**，等级决定词条**强度**，两者分离便于独立调平衡。

### 2.5 掉落规则

| 触发 | 规则 |
| --- | --- |
| 普通击杀 | 8% 概率掉落 |
| 通关（每 10 杀） | **必定**掉落 1 件，品质权重上浮（精英/腐化变体提升 1 档权重） |
| 背包已满 | 自动折算为金币（不打断战斗） |

按现有节奏（约 1 杀/秒级）估算：**约 12 杀 = 1 件**，即每关约 1 件保底 + 少量随机。
不会出现「背包瞬间爆满」，也不会「半天不出货」。

### 2.6 背包与自动装备

**背包 12 格**，右栏列表滚动显示。

```
默认行为（省心）
  ├ 新装备若比当前槽位更强 → 直接装备，旧装备进背包
  └ 背包满 → 最弱的一件自动分解成金币

可选操作（想调才调）
  ├ 点单件 → 装备
  ├ 「一键最优」→ 按加权分选出四槽最强组合
  └ 长按/点击「分解」→ 换成金币
```

**关键：默认不需要玩家动手。** 这既符合「全程无需操作」的产品定位，
又保留了想钻研的玩家手动优化的空间。

### 2.7 属性如何接入（架构关键点）

现在 `derive.atk()` 直接读 `state.hero.atkBonus`，而 `atkBonus` 被技能**直接修改**。
如果装备也去改 `atkBonus`，那么「换装 / 升级 / 卸下」就要做减法回滚，容易出 bug。

**正确的接法是把装备加成做成独立一层，只读不写：**

```js
// 现有
atk: () => baseAtk + state.hero.atkBonus + (level-1) * atkPerLevel

// 改造后
atk: () => baseAtk + state.hero.atkBonus + gear.atk + (level-1) * atkPerLevel
```

`gear.*` 由 `equip` 服务在**装备变化时**重算一次（不是每帧算）。
好处：

- 技能逻辑零改动
- 换装是幂等的：先清零再加总值，不存在回滚错误
- 存档只需存「装备了哪几件的 id」，`gear.*` 在读取后重建

## 3. 数值与平衡

### 3.1 当前经济基准（实测公式推算）

| 关卡 | 每杀金币 | 每关（10 杀） |
| --- | --- | --- |
| 1 | ≈3 | ≈30 |
| 6 | ≈26 | ≈260 |
| 12 | ≈40 | ≈403 |
| 24 | ≈97 | ≈968 |
| 48 | ≈559 | ≈5588 |

### 3.2 装备强度（实测修正）

**原始设计目标**是「满配约 +40%~60% 战力」。**实测后证明这个目标偏高**，已下调。

用 `scripts/calibrate-gear.js` 模拟「逐关推进 + 自动装备 + 买最便宜技能」的普通玩家：

| 关卡 | 等级 | 技能 atk | 装备 atk | 装备 hp | 攻速 | 暴击 | DPS 无装 | DPS 有装 | **增益** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 6 | 9 | 4 | 2 | 16 | 4% | 2% | 39.5 | 45.5 | **+15%** |
| 12 | 13 | 7 | 4 | 28 | 6% | 3% | 67.7 | 80.7 | **+19%** |
| 24 | 20 | 10 | 9 | 49 | 9% | 5% | 132.3 | 169.5 | **+28%** |
| 36 | 29 | 13 | 12 | 70 | 15% | 6% | 216.0 | 284.8 | **+32%** |
| 48 | 42 | 17 | 19 | 91 | 17% | 8% | 358.0 | 485.9 | **+36%** |

**为什么下调**：初版系数（atk `per=0.5`、hp `per=3`、speed `per=0.35`、crit `per=0.25`）
实测增益从 **+77% 涨到 +110%**，而且随关卡无限增长——因为装备强度按 `ilvl=stage`
线性涨，而等级带来的攻击力涨得慢。这会让免费掉落的装备彻底压过金币买的技能。

整体 ×0.33 后落在 **+15% ~ +36%**，随进度温和上升，不压过技能。

### 3.3 物品等级与掉落品质

```
ilvl = 当前关卡 stage
品质权重随 stage 缓慢上浮（stage/10 加到稀有及以上）
精英/腐化变体额外 +1 档权重
```

## 5. 存档与迁移

### 5.1 v1 → v2

```js
// v2 新增字段
{
  v: 2,
  equipped: [id0, id1, id2, id3],   // 四槽的物品 id，未装备为 0
  bag: [item, ...],                  // 背包（≤12）
  bagCap: 12,
  nextId: 421                       // 物品自增 id
}

// 单件物品紧凑编码（数组而非对象，省体积）
item = [id, slot, rarity, ilvl, [affixIdx, value, affixIdx, value, ...]]
```

**体积实测**（按真实字段跑过一遍）：

| 场景 | 字节数 |
| --- | --- |
| 当前 v1 存档（12 级、113 杀） | 226 |
| v2 满配（4 件已装备 + 8 件背包） | **476**（+250） |
| 单件物品平均 | **20.8** |
| 占 64KB 上限 | **0.7%** |

数组编码比对象编码省得多。即使背包满 12 格 + 四槽全满，也只用到 0.7% 配额。

### 5.2 迁移规则

```js
migrate(d):
  if (d.v === 1) {
    d.v = 2;
    d.equipped = [0, 0, 0, 0];
    d.bag = [];
    d.bagCap = 12;
    d.nextId = 1;
  }
```

老玩家升级后**空手继续**，进度不丢。这是必须保证的。

### 5.3 校验（沿用现有 `sanitize` 风格）

- `equipped` 长度必须是 4
- `bag.length` 钳制到 `bagCap`
- 每个 `ilvl` 钳制到 `[1, 9999]`
- 品质索引钳制到合法范围
- 非法物品**整件丢弃**，不让半个坏数据进背包

## 7. 风险清单

| 风险 | 严重度 | 缓解 |
| --- | --- | --- |
| 数值失控（装备过强，战斗变秒杀） | **高** | 先只装 1 个槽位跑通，再逐个开；每加一个槽位跑一次 1~50 关 DPS 校准 |
| 背包 UI 在小屏挤压 | 中 | 背包固定 12 格 + 滚动；`maintain` 现有响应式是否够用需实测 |
| 存档迁移出错导致掉档 | **高** | 迁移前后各写一次备份键；`apply()` 加 try/catch，失败走全新存档而非清空 |
| 掉落太频繁打断节奏 | 中 | 自动装备 + 满了自动分解，保证不掉落时不弹窗、不阻塞 |
| 老玩家回归看到空装备栏失望 | 低 | 首次进入送一件 ilvl 匹配的「普通」武器 |
| 与「全程无需操作」冲突 | 中 | 默认全自动；手动操作是**可选**而非必需 |

### 7.1 性能

装备重算只在**装备变化**时触发（O(4)），不进战斗循环。
渲染侧不新增绘制，仅 UI 列表重排。预计帧时影响 < 0.05ms。

## 8. 三个方案对比

### 方案 A：轻量版（推荐先做）

- 4 槽位、3 品质（普通/精良/稀有）、3 词条
- 只有自动装备，**没有背包**（新装备直接比较，差的丢弃折金币）
- 存档只加 `equipped`

| 维度 | 评估 |
| --- | --- |
| 工作量 | **约 180 行，1 次迭代** |
| 玩家决策 | 低（但至少有「换不换」的即时反馈） |
| 风险 | 低——没有背包就没有 UI/存档压力 |
| 缺点 | 没有收集乐趣，装备只是数值滑块 |

### 方案 B：完整版（本文主方案）

- 4 槽位、5 品质、5 词条、12 格背包、一键最优、分解

| 维度 | 评估 |
| --- | --- |
| 工作量 | **约 430 行，2~3 次迭代** |
| 玩家决策 | 高——这是真正能留住玩家的部分 |
| 风险 | 中——数值与迁移是主要坑 |
| 缺点 | UI 占满右栏，与技能页争夺空间 |

### 方案 C：不做

- 删除装备页，改文案为「本作专注于极简放置」

| 维度 | 评估 |
| --- | --- |
| 工作量 | **约 10 行（删代码）** |
| 玩家决策 | 保持现状（无） |
| 风险 | 零 |
| 缺点 | 放弃了唯一能增加主动性的系统 |

## 9. 我的建议

**做方案 A，跑一周看留存，再加到方案 B。**

理由：

1. 装备系统对**放置游戏**的留存价值主要来自「回来时有东西可整理」。方案 A 已经提供了即时反馈（打得动/打不动），但没有「整理」。
2. 但方案 B 的复杂度集中在背包与存档，这两块一旦出 bug 会**掉档**——这是最不能接受的事故。
3. 所以正确顺序是：先用 A 验证数值曲线（也是 B 必经的一步），再补背包。

**不建议直接上 B。** 数值没校准就加背包，等于把一个可能失控的系统放大两倍。

### 关键设计决定的理由

**装备加成不写回 `state.hero.*Bonus`。**
那是技能的领地，如果两边都写，换装就要做减法回滚，极易出 bug。
改成独立一层 `state.gearBonus`，由 `recompute()` 在装备变化时**整体重算**，
天然幂等。

**掉落放在换关之后结算。**
这样通关那件装备的 `ilvl` 已经是新关卡的，玩家立刻感到「变强了」。

**非法装备整件丢弃，而不是钳制。**
半个坏数据（比如 4 条重复词条）修好也没意义，直接丢掉更安全。

### 实测验证

| 项 | 结果 |
| --- | --- |
| 90 秒真实循环 | 无异常，26 击杀，4 次掉落 |
| 存档往返（写→读→apply） | v2，322 字节，四槽逐字节一致 |
| v1 → v2 迁移 | 版本升到 2，level/gold/stage/kills/atkBonus 全部保留 |
| 非法存档 | 4 个坏槽（越界槽位、负值、超限值、重复词条）全部丢弃 |
